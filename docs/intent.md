# intent：my_coding_agent Phase 2——会话持久化 + 上下文压缩

- 问题：Phase 1 的 messages 数组活在内存里，进程一退全丢；上下文只增不删，长任务必撑爆窗口；max-steps 硬截断不体面（模型没机会收尾）。pi 研究结论（树+投影 / 合法切点两级摘要）落地成自研实现——面试可讲。
- 用户/场景：自己终端跑多轮任务；进程重开会话能续；长任务上下文自动压缩不爆窗。
- 输入 → 输出：
  - 输入：同 Phase 1（终端一句话任务 + GLM API）+ 新增 `--list` 列历史会话、`--resume <id>` 续跑
  - 输出：同 Phase 1 + 新增 `sessions/<时间戳>-<id>.jsonl` 树文件（追加写，原文永存）
- 该拦什么（反例）：
  1. 切点永不落在 assistant(tool_calls) 与其 tool 结果之间——messages 数组不自洽 = 下一圈被 API 400 拒收
  2. 压缩不销毁原文——摘要只换投影，compaction 条目进树，原条目原地不动
  3. max-steps 到顶先软着陆（给模型一次强制文本收尾的机会），硬截断只做异常兜底
  4. 会话文件缺行/损坏 → fail-loud 拒加载，不静默吞
- 该放什么（正常场景）：任务 → 多圈循环 → 条目逐行追加进树 → 退出重进从树投影重建上下文续跑 → 超限自动压缩（摘要进树）→ 收尾
- 验收标准（5 条，每条可验证）：
  1. 多圈任务 → `sessions/` 出 .jsonl；退出重进 `--list` 能列出、`--resume` 续跑后模型知道上次干了什么
  2. 临时调高 `GLM_RESERVE_TOKENS` 压低阈值 → 触发压缩：树里新增 compaction 条目、原条目仍在
  3. 压缩后发出去的 messages 以摘要开头，且 tool_calls/tool 成对——不 400
  4. 压缩后任务继续跑完，最终回答正常
  5. `GLM_MAX_STEPS=3` 跑复杂任务 → 看到软着陆收尾，不是无情硬截断
